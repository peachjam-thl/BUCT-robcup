# 指令看门狗（上位机侧）

日期：2026-11-18。文件：[tools/cmd_vel_watchdog.py](../tools/cmd_vel_watchdog.py)，离线检查：[tests/check_cmd_vel_watchdog.py](../tests/check_cmd_vel_watchdog.py)。

> 本页保留旧版实现及历史实测。当前入口见[门控与统一启动](D3门控与统一启动.md)：新链路输入/cmd_vel、输出/cmd_vel_safe，默认禁动，基本架空流程已有实测，其他故障待验收。两者不能同时运行。旧版同Topic自订阅会刷新活动时间，文中“20Hz持续补零”不能仅由纯逻辑测试证明；controller_death_test实际模拟停发消息，并非真正进程猝死。历史近零反馈证据也不替代四轮目视停转。

## 为什么需要

2026-11-18架空实测：停发速度指令后，1.5 / 3.0 / 5.0 s窗口均未观察到近零反馈，5s轨迹仍约0.05m/s，随后探针主动发零速才得到零反馈。因此不能依赖当时配置自行超时停车；没有对无限时间行为或真正进程强杀作实测结论。

看门狗补的就是这一段：**指令静默超过阈值，就替控制源补发零速**。

## 旧版行为与局限

- 订阅并发布同一个 `/cmd_vel`（默认，可用 `--topic` 改）。
- 静默超过 `--timeout`（默认0.4s）尝试补零。定时器默认20Hz，但自身零速被同话题订阅接收后也会刷新计时；不能将定时器频率写成实际持续零速输出频率。
- 启动与退出会尝试发零；不能保证电机停转或覆盖驱动故障。
- 收到非零指令 → 解除保持，记 `WATCHDOG_RELEASE`。
- 正常退出前尝试连发5次零速，不保证强杀或通信失效时生效。
- 日志关键字：`WATCHDOG_START` / `WATCHDOG_STOP` / `WATCHDOG_RELEASE`。

## 启动

```bash
python3 /tmp/cmd_vel_watchdog.py --timeout 0.4 --rate 20
```

需要在已加载 ROS 环境的 shell 里运行；与底盘驱动同时保持运行。

## 验证（2026-11-18 实机，四轮架空）

**联测**：与探针的断流检查配合（探针需加 `--watchdog`，它只允许一个名为 `cmd_vel_watchdog` 的额外发布者）：

```bash
python3 /tmp/base_forward_probe.py --axis x --speed 0.05 --duration 3 \
  --check-silence-stop --silence-window 1.5 --confirm-wheel-stop --watchdog \
  --log-csv /tmp/silence_wd-1118.csv --evidence-out /tmp/silence_wd-1118.md
```

结果 `SILENCE_STOP_OBSERVED`：最后一条指令后约 0.96 s 反馈近零。同样命令在无看门狗时是 `SILENCE_STOP_NOT_OBSERVED`（5 s 不停）。

**历史“控制器猝死”记录（实际为指令静默）**：[tools/controller_death_test.py](../tools/controller_death_test.py)以0.05m/s发布2s后停发，进程继续观察而非当即退出或强杀。历史日志在约0.4s记补零、约0.9s反馈近零；未由此验证真正进程猝死、计算板掉电或MCU独立停车。

## 边界（别把它当失联保护）

- 只覆盖"控制器进程退出 / 话题静默"。驱动崩溃、串口断开、计算板掉电、MCU 失效都盖不住。
- 看门狗与驱动同一台主机、同一个 ROS 域，不是独立保护；`SILENCE_STOP_OBSERVED` 也不能用来证明 MCU 有独立超时。
- 多个控制源同时发 `/cmd_vel` 时不仲裁优先级，只看"有没有消息"；D3 要统一运动出口。
- 目前需手动启动。启动文件里没集成，忘了启动就等于没有保护。
